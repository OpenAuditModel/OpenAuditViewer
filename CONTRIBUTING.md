# Contributing to OpenAuditViewer

Thank you for considering a contribution.

This is a viewer, not a second implementation of the specification. The analysis it performs —
schema validation, privacy linting, digest and chain verification, profile conformance — is ported
from the [OpenAuditModel](https://github.com/OpenAuditModel/OpenAuditModel) conformance tooling and
must keep giving the same answers. That constraint shapes most of the rules below.

Read [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Do not report security issues in the public tracker;
see [SECURITY.md](SECURITY.md).

## Development setup

Requires Node.js 22 or newer. A desktop build additionally needs the Rust toolchain, and on Windows
the MSVC build tools ("Desktop development with C++").

```bash
npm install
npm run dev            # frontend only, in a browser
npm run tauri dev      # the desktop application
npm run demo-logs      # generate demo-logs/ to click around in
npm run verify         # what CI runs: validator, types, tests, formatting
npm run tauri build    # release binaries
```

`npm run verify` before pushing. TypeScript is strict and CI treats a type error as a failure.

## What belongs here, and what does not

**The viewer never transmits audit content.** There is no telemetry, no crash reporting, no update
ping that carries content, and no call to a remote validation service — including the project's own
MCP endpoint. Every check runs in this process. A change that sends event data to a service will not
be merged, however convenient the feature.

**Reading from a source the operator chose is a different thing, and is allowed.** A folder today; a
message broker someone points the app at is a legitimate future source. The rule is about where data
goes, not about whether a socket exists. An ingestion source has to hold the same line, and two
constraints follow from it:

- The connection belongs in the Rust process, not the webview. Granting the renderer network access
  would widen the blast radius of any rendering bug and force `connect-src` open in the
  Content-Security-Policy; passing received events over IPC keeps both closed.
- Broker credentials would be the first secret this app holds. They belong in the OS keychain, not
  in `localStorage` beside the theme preference, and they are never written to a log or an export.

**The viewer never claims more than the data says.** Two recurring examples:

- Events are grouped into flows only by `request.traceId` and `request.correlationId`, because
  those are declared by the producer. Grouping by "same resource" or "same actor" would present a
  guess as a fact.
- Chain verification groups strictly by `integrity.chainId`. An event that declares no chain is
  reported as unassigned rather than being inferred into a chain by ordering.

**Findings never contain the value that produced them.** A privacy message says which rule fired
and at which JSON Pointer, never a preview, prefix or decoded claim. Tests assert this.

**A clean result is never presented as a clearance.** Wording matters here: the app says what was
checked, not that the data is safe.

## Keeping parity with the specification tooling

`src/lib/privacy/`, `src/lib/integrity/` and `src/lib/profiles/` are ports of files in the
canonical repository. The vendored schema (`src/schema/`) and profile definitions
(`src/profiles/`) are copies of published documents.

- Every intentional divergence from the original is documented in a comment at the top of the ported
  file. Adaptations so far: schema validation calls this app's validator directly rather than an
  injected one, digest calculation is asynchronous because Web Crypto is, Node's `Buffer` is
  replaced by browser equivalents, and signature verification is omitted.
- **Do not "improve" ported analysis logic in place.** If a rule or a check is wrong, it is wrong in
  the specification tooling too — fix it there, then re-vendor. A viewer that is quietly stricter or
  more lenient than the CLI is a bug even when its answer seems better.
- Refresh vendored files with `npm run sync-vendored -- ../path/to/OpenAuditModel`. It reports what
  changed and regenerates the precompiled validator. A new upstream profile is reported but not
  adopted automatically, since adopting one also means registering it in `src/lib/profiles/index.ts`.

## The precompiled validator

`src/schema/validate.generated.js` is generated by `tools/generate-validator.mjs` and committed.
Do not edit it by hand.

It exists because Ajv builds validators with `new Function`, and the app ships a
Content-Security-Policy without `unsafe-eval` — in an application whose purpose is opening untrusted
files, allowing strings to become code is the wrong trade. CI regenerates the file and fails if the
committed copy differs, and separately fails if the built bundle contains runtime code generation.

## Tests

`src/lib/__tests__/` covers the analysis logic. Assertions are deliberately specific — a privacy
test names the rule identifier, an integrity test names the finding kind — because a test that only
asserts "it failed" passes for the wrong reason as easily as the right one.

A change to analysis behaviour needs a test that would have failed before it. A change to hostile
input handling needs one that feeds the hostile input.

The demo dataset (`tools/generate-demo-logs.mjs`) is deterministic and self-checking: it asserts
that the data it wrote still exercises what it claims to — an intact chain, a broken chain, specific
privacy rules, conforming and violating profile cases. Extend it when adding a feature that needs
something to look at.

Every value in the demo data is invented, and credential-shaped strings are recognisably fake. Never
commit a real audit log, and never add one to a test fixture or a bug report.

## Pull requests

1. Branch from `main`.
2. Keep the change focused.
3. Run `npm run verify`.
4. Update [CHANGELOG.md](CHANGELOG.md) under `Unreleased`.
5. Explain the reasoning in the description. For a decision of consequence — a new grouping rule, a
   deliberate divergence from the CLI, a change to what the app claims — say what the alternatives
   were and why they were rejected.

Describe limitations plainly in both code comments and user-facing text. This project would rather
say "not checked" than imply a guarantee it cannot make.

## Releasing

1. Move the `Unreleased` entries in [CHANGELOG.md](CHANGELOG.md) under the new version.
2. Set the same version in `package.json`, `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json`.
   All three are shown in the app's About panel, and disagreeing versions make a bug report useless.
3. Push a `v*` tag. The release workflow rebuilds, re-runs the tests, and attaches the portable
   Windows executable and its SHA-256 to a **draft** release.
4. Read the draft, then publish it by hand.

The draft step is deliberate. The binary is unsigned, so publishing one is the moment the project
asks strangers to click through a SmartScreen warning; that should be a decision, not an automation.
